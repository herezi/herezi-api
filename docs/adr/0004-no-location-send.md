# ADR 0004: 사용자 위치를 서버로 보내지 않는다 (지역 데이터 파일 + 기기 계산)

| 항목 | 내용 |
|---|---|
| 상태 | 승인됨 (사용자 결정, 2026-11-25) · **구현 완료** — 좌표 엔드포인트 제거 (2026-11-25, openapi 0.11.0, TECH-PLAN v1.10) |
| 날짜 | 2026-11-25 |
| 대체 | [TECH-PLAN.md](../product/TECH-PLAN.md) v1.5 §4의 좌표 기반 조회(`/v1/spots` 근처, `/v1/spots/map`, `/v1/geo/reverse` — TECH-PLAN v1.10에서 제거) |
| 근거 | 이슈 #74, SERVICE-PLAN v1.4 §12 Q8, TECH-PLAN v1.6 §1·§4, [docs/legal/LBS-REPORT.md](../legal/LBS-REPORT.md) §9 |

## 맥락
- 사업자등록을 하지 않기로 했다(2026-11-25). 위치기반서비스사업 신고는 사업자등록이 전제라 사실상 할 수 없다(LBS-REPORT §3.1).
- 지금 구조는 앱이 요청마다 좌표를 서버로 보내고, 서버가 PostGIS로 반경·거리순을 계산한다. 이는 개인위치정보를 다루는 것으로 볼 여지가 크다(LBS-REPORT §1.1).
- 서울 데이터는 수천 건 수준이라 기기에서 전부 들고 계산할 수 있다.

## 결정
- 앱은 **사용자 좌표를 서버로 보내지 않는다.**
- 서버는 지역 단위 전체 데이터 `GET /v1/regions/{region}/spots`(현재 `seoul`)를 내려준다. 진행 중·90일 안 시작 + 종료 후 90일 안 항목, gzip, 강한 ETag/304, `Cache-Control: public, max-age=3600`. 서버는 메모리 캐시를 최대 10분마다 다시 만든다.
- 거리 계산·반경·지도 영역·필터·정렬·키워드 검색은 기기에서, 위치 이름은 기기 지오코더(iOS `CLGeocoder`, Android `Geocoder`)로.
- 상세(`/v1/spots/{id}`)·저장(`/v1/me/*`)은 좌표가 없으므로 그대로.
- 좌표를 받는 API는 openapi에 `deprecated`로 표시하고, iOS·Android 전환 후 지운다.
  → **2026-11-25 제거됨**: 두 앱이 지역 파일·상세·`/v1/me/*`만 부르는 것을 확인한 뒤 `/v1/spots`(근처)·`/v1/spots/map`·`/v1/geo/reverse`와 서버 역지오코딩 클라이언트를 지웠다. 옛 경로는 **410 Gone**(`code=gone`, 쿼리를 읽지 않음)으로 답해 옛 빌드(TestFlight 1–2, Play ≤4)가 분명히 실패하게 했다. 접속 로그의 좌표 축약은 방어용으로 남긴다.

## 대안
- **좌표를 거칠게(구 단위 등) 보내기**: 여전히 위치정보 전송이라 쟁점이 남는다.
- **사업자등록 + 신고**: 사용자가 하지 않기로 결정.

## 결과
- 좋음: 서버가 이용자 위치를 받지 않아 신고 대상에서 벗어날 가능성이 커진다(**미확인** — 위치정보지원센터 문의 권장, LBS-REPORT §9). 응답 즉시·오프라인 동작·서버 부하 감소.
- 비용: 앱에 동기화·캐시·기기 계산 로직이 생긴다(두 앱 모두). 첫 실행 때 지역 파일을 한 번 받아야 한다(크기는 TECH-PLAN §4). 데이터는 하루 1회 갱신 수준으로 늦다(원래도 수집이 하루 1회).
- 옛 빌드(TestFlight 1–2, Play ≤4)는 제거된 경로를 불러 목록·지도가 동작하지 않는다 — 테스터는 앱을 업데이트해야 한다.
- 지역을 넓히면 지역 파일을 늘린다. 서울 하나로도 파일이 너무 커지면 카테고리·기간으로 나누는 방안을 다시 검토한다.
