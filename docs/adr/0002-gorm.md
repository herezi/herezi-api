# ADR 0002: DB 접근을 sqlc에서 GORM으로 전환

| 항목 | 내용 |
|---|---|
| 상태 | 승인됨 (사용자 결정) |
| 날짜 | 2026-11-20 |
| 대체 | [ADR 0001](0001-go-stdlib-postgis-sqlc.md)의 "쿼리: sqlc" 항목 |
| 근거 | [TECH-PLAN.md](../product/TECH-PLAN.md) v1.1 §2 |

## 맥락
- ADR 0001에서 쿼리 계층으로 sqlc(SQL → 생성 코드)를 골랐다.
- 사용자가 ORM을 쓰기로 결정했다(2026-11-20). Go에서 가장 널리 쓰이는 GORM을 쓴다.
- 핵심 질의는 PostGIS 공간 질의(반경·거리순·bbox)라 ORM의 기본 쿼리 빌더만으로는 표현할 수 없다.

## 결정
- `gorm.io/gorm` + `gorm.io/driver/postgres`(내부적으로 pgx v5).
- GORM 모델(`spotRow`)은 `internal/store/postgres` 안에만 두고 `domain.Spot`과 변환한다. `domain`은 gorm을 import하지 않는다.
- **스키마의 기준은 goose SQL 마이그레이션**이다. `AutoMigrate`는 쓰지 않는다 — `geography(Point,4326)` 컬럼, GiST 인덱스, CHECK 제약을 정확히 표현할 수 없다.
- 공간 조건은 GORM raw 표현식으로 쓴다:
  - 좌표 읽기: `Select("ST_Y(geog::geometry) AS lat, ST_X(geog::geometry) AS lng, ...")`
  - 반경: `Where("ST_DWithin(geog, ST_SetSRID(ST_MakePoint(?, ?), 4326)::geography, ?)", lng, lat, radius)`
  - 거리순: `Select(... "ST_Distance(geog, ?) AS distance_m", point)` + `Order("distance_m, id")`
  - bbox: `ST_MakeEnvelope`
  - upsert: `clause.OnConflict{Columns: source, source_id}`, `geog`는 `gorm.Expr("ST_SetSRID(ST_MakePoint(?, ?), 4326)::geography", lng, lat)`
- 사용자 입력은 항상 `?` 바인딩으로 넘긴다(문자열 이어붙이기 금지).
- 단일 문장 쓰기뿐이므로 `SkipDefaultTransaction: true`, 로그는 앱 로거로 남기므로 GORM 로거는 끈다.

## 대안
- **sqlc 유지**: SQL이 그대로 보이고 타입 안전하지만 사용자 결정으로 제외.
- **ent, bun**: GORM 대비 사용 사례·자료가 적다.

## 결과
- 좋음: 별도 코드 생성 CLI(sqlc)가 필요 없다. 필터 조합(카테고리·무료·기간)을 스코프로 재사용한다.
- 비용: 공간 질의가 문자열 표현식이라 컴파일 시점 검증이 없다 → `storetest` 공통 스위트를 CI의 PostGIS 통합 테스트(`make test-integration`)에서 돌려 검증한다.
- AutoMigrate를 쓰지 않으므로 모델과 마이그레이션이 어긋나면 통합 테스트에서만 드러난다. 컬럼을 바꿀 때는 마이그레이션·`spotRow`·`storetest`를 같은 PR에서 고친다.
